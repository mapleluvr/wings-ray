## 1. 状态、依据与范围

本计划依据 [requirements-1010.md](../proposals/requirements-1010.md) 的当前使用例 A。需求文档第 1—4 节为已明确行为，第 5—6 节仍是建议，第 7 节仍有未决政策；本计划中的推荐选项不自动成为已确认需求。

代码核对基点：`hfut/infra-planning`，HEAD `ce1c0c15e14bafaed54f13e9ce6fab9a8053d1d1`。需求文件 SHA-256：`7793E2C5E11CC992AB327AE1B92D3D721A743DE474F8B599EA34CFC20987C8E4`。后续需求有修改时，先更新对应决策和验收用例，不沿用过期哈希作为依据。

本计划最初只获编写计划的授权。用户随后明确授权按 new-api 原有变更规范实施、由独立 reviewer 审查、由主 agent 修复并仅推送到 `mapleluvr/wings-ray`。下文保留设计与验收依据；第 11 节记录本次实现决策、验证和交付状态。服务部署、凭据配置和真实付费模型调用仍需另行授权。

首个实现范围建议为：**HTTP/SSE 文本 token 表达式计费，以及订阅／充值两种来源的按模型扣费调整**。该范围需要在启用配置前明确到请求入口和计费分支，不能仅凭模型名认为所有入口都适用。

- 复用现有订阅账户、充值余额、兑换码和用户支付偏好；不另建两个余额列或新钱包。
- 保留表达式作为模型标价的唯一价格来源。资金来源政策在宿主计费层作用于实扣，不改写标价表达式。
- `256k` 在例 A 中取 `256000`。管理员在已有表达式／阶梯编辑入口填写供应商要求的精确 token 阈值；需要时自行换算为 `262144`，不增加 k 换算控件。
- token 计价单位 `1M` 始终为 `1000000`，`QuotaPerUnit` 沿用系统配置，例 A 为 `500000`。
- 旧倍率／按次定价、`fixed()` 分支、图片、音频、Realtime、任务插件和违规费不由例 A 自动决定。共享代码调整必须保护这些原有路径，扩展收费政策需另行明确。
- 服务部署、真实付费模型调用、凭据配置和上游 PR 不在本次实施范围；代码提交、独立 review-fix 循环及向用户 fork 推送已经获得授权。

以下现有行为需要显式覆盖：

1. 订阅预扣要求 `amount > 0`。`NewBillingSession` 将非正预扣提升到 1 quota，`SubscriptionFunding.PreConsume` 使用构造时的 amount。即使倍率大于零，舍入后的预扣也可能为零，不能把计算值、内部 amount 和实际扣款记录混用。
2. `BillingSession.Settle` 区分资金来源提交与 API Key 调整；资金已提交但 Key 调整失败也可能返回 error。`PostTextConsumeQuota` 当前在结算前更新累计，结算错误后继续写计算额日志。新路径必须取得实际提交结果，不能根据一个 error 推断全部扣款成功或失败。
3. 当前 `hasBillableUsage()` 同时考虑 tokens、工具附加费和固定价格。金额拆分后不能用 `Dq == 0` 推断没有 usage；真实用量、零实扣和计量失败是不同状态。

## 5. 后端设计

### 5.1 标价和实扣分开计算

例 A 的分组倍率为 1，记：

```text
raw = 对实际归一化 usage 执行被冻结的表达式所得结果
U   = raw / 1000000 × QuotaPerUnit        # 未舍入的标价 quota
Lq  = Round(U)                          # Channel 计量 quota
Dq  = Round(U × r(model, selectedSource)) # 用户实扣 quota
R   = 资金来源实际成功预扣的 quota
结算差额 = Dq - R
```

`Round` 使用现有集中 quota 换算函数，不新增裸 `int` 转换。预扣使用 strict 变体，实际结算使用 checked 变体并记录饱和审计。标价与实扣各自检查有限值和上限；不能以折扣掩盖无效标价，也不能因加价溢出形成负扣款。

预估 U 从 `EstimatedQuotaBeforeGroup` 取得，包含现有预扣乘数；实际 U 从 `ActualQuotaBeforeGroup` 取得，不额外乘预扣乘数。若 D7 确定分组倍率进入标价，两个阶段都先乘实际生效的分组倍率，再分开计算 Lq、Dq。

- 不将来源倍率写入 `OtherRatios`，表达式路径不使用该机制。
- 不直接覆盖 `BillingSnapshot.GroupRatio` 为 group × source，这会丢失独立标价和真实分组的含义。
- 不从已舍入 Lq 再乘 r，也不从 Dq 除以 r 反推 Lq。
- 表达式求值失败时，`TryTieredSettle` 的既有返回值可能已经是实际预扣。新结果要标明 actual／estimated／reservation 来源，防止把折算后的 R 当作标价再打一次折。

### 5.2 配置、匹配与一致快照

优先在现有 `BillingSetting` 增加两个模型到数值的映射。以下为候选键名，实施时保持后端、草稿和前端一致：

```json
{
  "billing_setting.subscription_multiplier": { "A": 0.5, "B": 1, "C": 1.5 },
  "billing_setting.wallet_multiplier": { "A": 0.9 }
}
```

数值为扣费倍率，不是减免百分比。C 的钱包缺失不表示继承 C 的订阅 `1.5`；若采用 D3 推荐值则解析为钱包 `1`。

实现内容：

1. 扩展 `setting/billing_setting/tiered_billing.go` 的注册、默认空映射和只读访问；请求只读取所需模型的一致快照，不持有可变全局 map。
2. 将新键纳入 `modelPricingOptionKeys`、配置／生效草稿、版本哈希、校验、完整草稿替换和重置；不绕过现有 `expected_version` 事务入口。
3. `UpdateModelPricingOptions`、旧 `PUT /api/option/` 和任何批量 option 写入都执行同样的范围／数值校验，不能只保护新 UI。
4. 两来源倍率、表达式及其版本需要一致发布到请求读取路径。不得让一次保存的不同字段逐项可见后，被请求拼成混合版本；启动加载、定期 SyncOptions 和保存后发布均需覆盖。优先采用受保护的不可变模型计费快照，避免重写通用配置框架。
5. 新模型、只有倍率的模型条目、删除来源覆盖、重置默认、切换旧计费模式、复制价格和导入／价格同步必须保留明确含义。推荐价格同步不覆盖本地资金政策，批量复制不默认传播另一模型的来源政策；最终复制／导入行为在 UI 中明确。
6. 非本次作用域的定价可以保留配置用于以后切回，但管理界面必须标明未生效。启用时依据 D7 明确入口，不能在共享结算函数中无条件应用倍率。

优先扩展 `RelayInfo` 与 `BillingSession` 现有状态，保存计费模型、版本、两来源倍率和成功选中的倍率。金额结果若由预扣、重试、结算和日志共同使用，可引入一个宿主金额结果类型；不增加通用策略框架。

### 5.3 候选来源预扣、重试和退款

保留「先求标价、后试资金来源」的顺序。在 `NewBillingSession` 的每个候选来源内部，从同一未舍入预估标价和被冻结的来源倍率计算该来源的预扣目标。

- 订阅不足后回退钱包，要按钱包倍率重新计算并检查用户余额及 API Key 预算；不能携带订阅预扣金额。
- 一个候选来源失败时，已产生的 token／资金变化必须按实际值回滚后才试下一来源；数据库错误不当作余额不足回退。
- 预扣成功后，来源、订阅 ID 和倍率在本请求内固定；渠道重试不重新选择更便宜的来源。
- `BillingSettler.Reserve(int)`、`Settle(int)` 的整数参数继续代表实际扣款 quota。转换发生在调用边界，避免同一个数在会话内部再次乘倍率，影响音频／图片等共享调用者。
- 分组重试从未舍入预估值重新计算该来源的实扣预留，再调用 Reserve。钱包信任旁路的实际 R 可以为零，但不能把信任旁路理解为免单。
- 区分预估标价、按来源计算的预扣目标和实际 R。订阅最低 1 quota、幂等请求命中的既有预扣记录、补充预留均按真实返回状态同步。
- 若保留最小 1 quota 的订阅预留，最终 Dq=0 时按实际 R 退差额；不得为了显示零而抹掉实际占用。若要求 `0x`／零预扣无需临时占用就能选订阅，则需专门扩展订阅选择／零金额记录契约，不能绕过模型校验。
- 退款使用原来源和实际记录，不重新读取当前倍率。沿用有幂等依据的订阅退款重试；钱包加余额操作不能盲目重试。

### 5.4 结算结果、日志及累计

扩展文本结算的金额结果，至少区分标价、应扣、实际成功扣款和计费状态。结算成功时：

| 消费方 | 金额 |
| --- | --- |
| 所选订阅／充值余额 | Dq |
| API Key 已用／剩余预算 | Dq，按 D7 推荐值；不缩放额度上限 |
| 用户累计消费 | 成功实扣 Dq，按 D7 推荐值 |
| 请求计数 | 保持既有定义，不因金额拆分重复计数；失败请求计数遵循 D5 |
| Channel 累计使用 | Lq |
| Usage log 主 quota、用户消费聚合、仪表盘 | Dq |
| 原始 token 及性能统计 | 真实用量，不乘 r |

新路径先取得资金提交结果，再更新按成功实扣计算的累计。对于资金已提交但 token 调整失败，以及资金补扣失败两类情况分别记录状态，不能统一标成全额失败或全额成功。Channel 在扣款失败时的计量时机遵循 D5；不要把两种独立数据库写入描述为一个分布式原子事务。

建议在现有 `LogOther` 公共业务区域保存一个版本化的资金计费对象，字段覆盖：计费模型、表达式 hash／既有冻结表达式、r、Lq、应扣 quota、已提交净扣款、资金与 token 状态、金额依据。字段名在实现前一次确定，日志 UI 和导出共用。归一化 token 与必要的计量来源用于复算，不保存额外提示词、原始请求正文或凭据；诊断和饱和信息继续放 admin 区域。

- 成功新日志的主金额以新的实扣结果为准，订阅 `subscription_consumed` 等兼容字段要一致，包括显式零。
- 旧日志不补造倍率和标价。仍按原字段显示；不能用当前配置反推历史金额。
- 以 `Log.quota` 为源的统计保留实扣含义；按 Channel 筛选仍是该 Channel 的用户实扣合计。Channel 列表的累计是标价计量，两者明确命名。
- 不新增从 JSON 中跨数据库求和标价的 SQL，也不为尚未要求的渠道标价时间序列新增列。若以后要求完整标价聚合，另行确定存储和迁移。
- 结算／退款幂等保证应写清作用域。当前会话内防重及订阅预扣 request_id 不等于跨进程、跨重启的完整资金账本；D5/D6 若要求崩溃后补偿，单独评估持久化设计。

## 6. 输出分段及计量证据

将 R5 与来源倍率分开实现：**输出分段决定 L，来源倍率随后决定 D**。不在资金代码里硬编码 T、6 或 12，也不为每种资金来源生成一份表达式。

### 6.1 精确分段

对于可信、同口径的实际 I、O，以及单路连续追加、不截断的生成：

```text
before = min(O, max(T - I, 0))
after  = O - before
输出标价 = (before * 6 + after * 12) / 1000000
```

本例纯文本表达式中的输出贡献可写成：

```text
min(c, max(256000 - len, 0)) * 6
  + (c - min(c, max(256000 - len, 0))) * 12
```

这是输出部分，不是完整 A 表达式；普通输入／缓存的阈值分配还依赖 D1。实施时保持价格与阈值常数由管理员表达式定义，不另建第二份定价表。

### 6.2 计量事实及兜底

先梳理 `BillingUsage.Source / Semantic / Estimated`、原始字段缺失、流的结束状态、请求 choice 数、各分支计数、推理 tokens 的供应商语义以及协议转换的保留情况。

- 完整可靠的单序列计数可用于精确分段；`Estimated=false` 或存在 `len`、`c` 两个数都不能单独作为证明。
- 确认输出全部在阈值后时按 12；已知非全后且触及／跨越边界、但无法拆分时整段按 6。
- 多 choice 的合计 O 不能直接接在单个输入后定位。没有各路计数时不宣布精确分段；若所有分支都确认从边界后开始，可按全部阈值后处理。
- 输出总数缺失、是否全后都无法确定、估算 usage 或生成内部截断不能靠默认零字段解决；按 D5 已确定的异常计量政策处理。

若现有事实不足，最小扩展应是**由宿主验证的计量事实**，描述输入总长是否可靠、输出计数是否可靠、是否一条连续序列。事实不含价格或模型阈值，不能由客户端请求头／`param()` 自报。表达式按这些 opt-in 事实和自己的 T 选择精确／兜底分支；不要用临时修改 `len`、`c` 的方式强迫命中低价档。

相关工作可能涉及 `pkg/billingexpr/types.go / compile.go / run.go`、宿主 usage 构造和日志。只在验证需要时扩展 `relaykit/dto` 的原始字段保留；不得将宿主资金政策放进 relaykit。增加事实时明确默认值、编译环境、旧表达式兼容和模拟器契约；同步已有 `expr.md`，不悄悄改变 v1 旧变量含义。

已有高级原始表达式编辑入口足以承载线性算术。可视化编辑器不认识的新结构必须保留原始模式，不将其往返转换成全量涨价的阶梯。后台模拟需明确区分人工选择的计量场景与真实上游证据。
